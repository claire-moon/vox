# v0.0.4 supersession record

v0.0.4 was an implementation and qualification candidate, not a published
release. It has no public `v0.0.4` release tag or release assets. Its original
checklist remains a historical record and must not be rewritten to make an
unperformed acceptance pass look complete.

The current release target is v0.0.5. It carries forward every unresolved
v0.0.4 gate, including the fifteen-minute four-slot soak, the memory and
conversation checkpoints, physical controller/audio acceptance, package
evidence, and protected-main release review. The v0.0.5 checklist is the only
place that may close those gates for a future public release.

## What stays preserved

- `V0.0.4_RELEASE_CHECKLIST.md` remains the contemporaneous candidate record.
- `docs/compatibility/MATRIX.md` retains its v0.0.4 evidence section as
  historical evidence, not as current release proof.
- `qa/V0.0.4-QUICK-FEEDBACK.txt` remains available for provenance. It is not
  included in a v0.0.5 package; the packager selects the form named by
  `VERSION`.
- The original pre-squash phase-2 head is retained by the annotated
  `archive/v0.0.4-phase2-stability` tag. That tag is archival only and must
  never be presented as a release tag.

## Erratum: memory and the canonical hash

The historical checklist and matrix used overly broad wording that suggested
saved history never reaches the canonical match hash. That is false. A match
opened from carried miner memory intentionally receives a different opening
condition and can hash differently from a first meeting. The controlled
`--load-self-test` starts from a canonical snapshot, so matching output across
pref paths proves only that port wall-clock metadata stays out of that stream.
It does not prove that memory is absent from every match.

The old records remain readable as contemporaneous evidence, with this erratum
as their interpretation. v0.0.5 QA and package evidence use the narrower,
correct boundary.

## What must not happen

- Do not retroactively tag or publish the v0.0.4 candidate.
- Do not transfer checkmarks or performance figures into a v0.0.5 release
  without reproducing them on the v0.0.5 candidate.
- Do not delete the historical branch/ref evidence or run garbage collection
  until the branch audit has been completed and the archival tag is present on
  the protected remote.
